## 2 项目目标与 NABCD 初稿

### 2.1 目标

1. 用户能够发布一个本地文件，发现持有该文件不同分片的设备，并从多个可达来源完成下载。
2. 当部分节点离线、变慢或返回损坏数据时，只要最终取得同一文件版本任意 k 个索引不同且校验有效的分片，仍能够正确恢复原文件。
3. 下载调度能够观察分片可用性与实时网络表现，调整来源和请求分配，并用可复现对照实验说明效果及局限。
4. 小组能够围绕同一组需求编号形成后续原型、任务、设计和测试证据。

### 2.2 NABCD

以下是立项讨论的假设，尚未开展用户访谈或竞品实测，不应作为已验证结论提交。

| 维度 | 初步表述 | 后续需要的证据 |
| --- | --- | --- |
| N 需求 | 在课程实验或小型协作网络中，文件可能分散在多台设备，设备在线与网络质量不稳定；用户需要看清可用来源并可靠取回文件 | 真实使用场景、现有共享方法的痛点及实际发生频率 |
| A 方法 | 协调服务记录设备和分片索引；客户端优先经 STUN 辅助建立 UDP 直连，失败后经服务端 UDP 中转，按分片分布与网络情况调度下载，再以 RS 恢复文件 | 交互原型、协议验证、可复现功能和性能实验 |

## 3 使用者与业务边界

### 3.1 角色

| 角色 | 目标与职责 |
| --- | --- |
| 文件发布者 | 选择本地文件，生成并发布元信息与分片，决定是否继续提供分片 |
| 下载者 | 查找已授权可见文件，选择保存位置，控制下载并查看结果 |
| 分片持有者 | 保留并向其他获准设备提供校验有效的分片，控制本机共享和带宽占用 |
| 系统维护者 | 配置协调服务与 STUN 地址，查看服务健康情况，维护实验配置和日志 |

同一客户端可以同时承担前三种角色。“小组成员”属于项目分工角色，真实姓名、负责人和截止日期在任务分解阶段确认。

### 3.2 协调服务与数据传输

- **服务端控制面**：客户端连接后分配 UUID，维护 UUID 与当前连接/会话的绑定、心跳及在线状态、文件清单、分片持有关系和候选端点，协调双方建立连接。
- **服务端中转数据面（MVP）**：同一 Linux 服务端承担直连失败后的 UDP 数据转发；与元数据 API 在职责、资源计量及错误分类上区分。中转仅转发当前传输，不承担文件长期保存，也不作为额外的 RS 分片持有者。
- **客户端数据面**：在 Windows 本机编码、存储、校验、上传和下载分片；优先客户端之间 UDP 直连，直连失败后通过服务端中转。
- **STUN 服务**：辅助发现映射地址并支持连接建立过程；不能仅凭一次 STUN 响应认定另一端可达。
- **SQLite**：持久化协调元数据。建议不存储文件内容或分片载荷。

用户明确指定的是文件数据走 UDP。控制面使用何种协议尚未明确；建议 Echo 提供 HTTPS API，必要时增加事件通道。该建议不构成改用 TCP 传输文件的授权。中转路径仍遵守 UDP 文件传输约束；如果客户端到服务端的 UDP 也被阻断，中转同样可能失败，第一版不承诺覆盖所有网络。

### 3.3 第一版范围与细化需求

**MVP 纳入：**

- 首发仅 Windows 客户端和 Linux 服务端；不额外细化系统版本；构建与测试记录实际 CPU 架构
- 一个兼具协调和中转能力的服务端实例、一个设备协作空间；连接后由服务端分配 UUID，无账号注册/登录体系，保留连接与会话校验
- 本地单文件发布（首期最大 1 GiB）、文件列表与基本筛选、指定文件版本下载
- RS 编码、分片分发与持有关系上报、任意 k 个有效分片恢复
- 多源并行下载、依据可用分片和网络表现调整来源
- UDP 上的可靠交付、拥塞响应、会话安全、STUN 辅助打洞及失败后的服务端中转
- 暂停、继续、取消、重试，以及重启后保留已校验的完整分片
- 连接失败、来源不足、磁盘错误等异常的可理解提示
- 支持验收所需的状态展示、结构化日志和统计导出

**P1 可选增强：**扩展到 Windows 客户端/Linux 服务端以外的平台、跨重启保留未完成分片内部进度、更丰富的搜索、自动分片再分布、自动修复冗余、多个文件的高级队列策略。

**本轮不纳入：**云盘式目录同步、文件在线编辑、挂载文件系统、DHT 全去中心化发现、服务端集群、无限设备规模、匿名公共资源市场、移动端、用户账号系统和服务端永久文件存储。UDP 受限时改用 TCP/其他传输不纳入当前范围；具体中转协议/库在设计阶段选择，不把完整 TURN 实现当作已经确定的要求。

## 4 概念与数据规则

### 4.1 术语

| 术语 | 本文定义 |
| --- | --- |
| 设备 / Peer | 运行客户端并在连接服务端后获分配 UUID 的实例；UUID 用于标识，不是秘密凭据，也不是用户账号 |
| 会话 | 经验证的连接上下文，绑定服务端分配的 UUID；UUID 保存在本地配置文件并在重连时复用，秘密恢复凭据与 UUID 分开 |
| 中转路径 | 来源 Peer → Linux 服务端 → 下载 Peer 的 UDP 转发路径；来源身份与分片索引仍归属原 Peer |
| 文件内容摘要 | 对原始完整文件计算的摘要，用于最终完整性验证 |
| 文件版本标识 | 唯一绑定一份不可变清单的标识；文件内容相同但编码参数不同，应能区分 |
| 清单 / Manifest | 文件长度、摘要、编码参数及所有分片索引、长度、摘要等元信息 |
| 分片 / Chunk / RS shard | RS 编码得到的 k+m 个逻辑分片之一；本项目在需求层统一使用“分片” |
| 传输块 | 为发送一个分片而进一步切分的网络传输单位；不是独立的 RS 分片 |
| 有效分片 | 属于目标版本、索引和长度合法，且摘要校验通过的完整分片 |
| 可用来源 | 对目标分片有持有声明，且当前连接和数据请求可成功的 Peer |

### 4.2 不变量

1. 第一版一个文件对应一组 k+m 个逻辑分片：已确认基线 k=4、m=2，首期最大文件 1 GiB。其他参数的开放范围需重新评审，并受所选 RS 实现约束。分段传输不改变“任意 k 个逻辑分片恢复整个文件”的课程验收口径。
2. 只有同一文件版本、同一组编码参数下的有效分片才可共同解码。同一个分片的多个副本只计为一个独立索引；k 台在线设备不等于已有 k 个可恢复分片。
3. 清单至少包含格式版本、文件显示名称、原始长度、文件内容摘要、k/m、编码格式标识、分片索引及各分片长度和摘要、补齐规则所需信息。任何影响解码的参数变化都产生新版本。
4. 清单必须通过可信且经过校验的控制通道取得；摘要只能验证与清单的一致性，不能独自证明发布者身份。接收方不得信任来自任意 Peer 的替代清单。
5. 分片分布独立于不可变清单记录，包含文件版本、分片索引、设备、声明时间及当前会话。设备重连后的旧声明需重新确认。
6. 设备“在线”只表示协调服务近期收到有效心跳。“可达”“持有有效分片”“具有足够独立分片”是不同状态，应分别判断。
7. 发布不等于已复制到其他设备；编码也不等于已有冗余容灾。只有实际完成分发并确认持有，才可展示对应分布。一个设备可持有多个分片，设备故障与分片丢失数量不能简单等同。
8. 完成下载的条件为取得足够有效分片、成功解码、验证原始长度和整文件摘要并写入目标文件。临时数据不得以成功文件显示。

后续如果改成多个独立 RS 编码组，必须修改清单和验收口径：每组都需要至少 k 个有效分片，不能声称全文件任意 k 个传输块即可恢复。该变更需重新评审。

## 5 主要业务流程

### UC-01 设备上线

配置服务端和 STUN 地址 → 客户端连接服务端 → 服务端分配 UUID 并绑定已验证连接/会话 → 上报候选端点 → 周期发送心跳 → 同步本机实际有效分片。无需用户注册或登录。

服务端拒绝不匹配当前会话的 UUID 声明，不能把“知道 UUID”当成身份验证。网络恢复后重新建立合法连接；UUID 持久化保存并沿用，客户端须用独立本地秘密凭据证明恢复权限，不能仅凭 UUID 恢复。本地任务与有效分片仍按 FR-016 恢复并重新上报；服务端重启后不直接把旧记录标为在线。

### UC-02 发布与建立多节点分布

发布者选择文件 → 检查可读性和可用空间 → 生成分片及清单 → 上报有效持有关系 → 其他获准设备按选定分片接收并保留 → 接收方校验通过后上报新持有关系。

第一版允许由操作者选择要保留的分片，不要求自动均衡放置。接收方须主动参与共享，不允许远程任意写入未授权目录。发布期间原文件变化应中止本次发布并要求重试。

### UC-03 多源下载与恢复

下载者选择版本与保存位置 → 取得可信清单和候选来源 → 检查已有有效分片 → 发起连接协调和双向 UDP 探测 → 直连成功则使用直连，直连超时/失败则请求服务端中转 → 从多个可达 Peer 请求不同分片 → 持续观察吞吐、往返延迟和失败情况 → 调整来源 → 校验分片 → 达到 k 个独立有效分片后恢复并验证完整文件 → 展示完成。

直连失败后按有界超时切换中转；中转也失败时显示具体原因并退避、换源或重试。分片缺失或 Peer 离线不能靠中转补齐；不足 k 个可获得的不同分片时进入“等待来源”，而不是误报完成。取消后释放直连及中转资源，是否清理本任务缓存由用户选择。

### UC-04 暂停与恢复

用户暂停 → 停止安排新传输并保存有效分片记录 → 用户继续或重新启动客户端 → 复核已有分片与清单 → 重新发现来源 → 从缺失分片继续。

MVP 只承诺跨重启保留已校验的完整分片，未完成分片可重新下载。用户应能看清实际可复用的进度。

### UC-05 停止共享与故障处理

持有者停止共享 → 立即停止接受新分片请求并撤销持有声明 → 对进行中的请求给出终止状态 → 下载者换源。

异常退出时由心跳超时和请求失败共同淘汰来源。撤销发布不远程删除其他设备已经取得的文件；删除本机缓存也不能影响无关文件。

## 6 功能需求

下列条目细化 MVP 行为；已确认范围见 SRC-04，其余细节仍需小组评审。每项的“验收”是后续测试应验证的结果，而非已通过的测试。

### 6.1 设备与协调

**FR-001 UUID 分配与会话绑定**  
第一版不提供用户账号系统。客户端连接服务端后获得由服务端分配的 UUID，用于在线状态、来源和持有关系标识；UUID 与当前已验证连接/会话绑定，不能充当秘密凭据。连接绑定、会话令牌或成熟握手方案的具体选择留到设计阶段。  
验收：连接成功可取得合法 UUID，不同活动客户端标识互不冲突；仅提交另一客户端的 UUID 不能修改其在线状态或分片记录。UUID 持久化保存在本地配置文件并在重连/重启时复用；独立的本地恢复凭据不得出现在日志或界面中。

**FR-002 心跳与状态过期**  
协调服务接收心跳，按配置的期限区分在线、离线和待确认状态，返回最近状态更新时间。  
验收：停止心跳后，在规定期限内不再被新任务当作在线候选；恢复有效会话后重新上线。具体目标见 NFR-002。

**FR-003 分片持有关系**  
客户端上报、查询、撤销自己持有的有效分片；服务端支持同一分片对应多个设备，保留各自的新鲜度。  
验收：两台设备持有同一索引时显示两条来源、一个独立分片；撤销一台后另一台仍可用；重复上报不产生重复关系。

**FR-004 连接协调与可达性**  
服务端向获准的双方提供候选端点及会话信息，支持双方 UDP 探测；客户端记录实际连接结果，直连失败后自动尝试 FR-026 的中转。  
验收：在受支持的实验网络完成连接；候选失效或 STUN 不可用时有超时和可识别错误；不能只凭心跳或 STUN 响应显示已连接。

### 6.2 文件与分片

**FR-005 文件发布**  
客户端发布用户显式选择的本地单文件，读取权限、空文件和处理过程中的变更均有明确处理。  
验收：不超过 1 GiB 的有效文件生成清单，超过上限明确拒绝；不可读文件和编码期间被修改的文件不发布为成功；空文件可按第 8 节规则完成往返。

**FR-006 清单校验与版本隔离**  
客户端和服务端验证清单结构、长度、索引、参数范围与支持的格式版本，不混用不同版本的分片。  
验收：缺少摘要、重复索引、越界参数或不支持格式被明确拒绝；同名不同内容文件可区分；同内容不同编码参数不发生误解码。

**FR-007 RS 编码和恢复**  
按清单生成 k+m 个分片，使用任意 k 个有效不同索引恢复，并按原始长度去除补齐数据。  
验收：对已确认 k=4、m=2 的小文件遍历全部 15 种四片组合，恢复结果逐字节相同；三片不足时不报告恢复成功；坏片和重复索引不计数。

**FR-008 初始分片分发**  
获准设备可主动从已有来源接收选定分片，校验并保留后才对外声明持有。  
验收：将六个索引分布到至少三台来源设备，发布者离线后，只要其他设备仍提供任意四个有效不同索引，新下载者仍可完成下载。

**FR-009 文件发现**  
客户端展示当前协作空间中获准可见的文件名称、大小、版本、独立分片候选数和来源新鲜度，并支持按名称或版本筛选。  
验收：可找到指定版本；同名文件不会被合并成一项；候选分片数量带有状态含义，不能当作当前必定可下载的保证。

**FR-010 本机共享控制**  
用户可停止提供某个文件或分片，查看实际共享内容与缓存占用，明确选择是否删除相关缓存。  
验收：停止共享后不接收新请求并更新分布；不会删除原文件、其他任务仍使用的缓存或目标目录外的文件。

### 6.3 下载与调度

**FR-011 下载任务创建**  
用户选择文件版本和保存位置后创建任务，检查目标目录、预计存储需求和同名文件冲突。  
验收：空间不足或无写权限时给出原因；覆盖已有文件必须由用户明确确认；重复点击不意外创建多个相同任务。

**FR-012 多来源并行下载**  
在存在多个可用来源时，可同时从至少两个 Peer 获取不同分片，且并发量可限制。  
验收：日志证明两条不同来源的有效数据传输时间发生重叠；最终文件一致；单一来源仍可降级完成，不强制凑足多个来源。

**FR-013 自适应来源选择**  
调度同时考虑独立分片缺口、来源分布和近期网络表现；网络变差或请求失败时调整后续分配，优先获取尚缺的有效索引。  
验收：控制一条路径降速或增加丢包后，在建议 10 秒内出现可解释的分配变化；有健康替代来源时继续推进；记录决策依据并与固定策略对照。性能目标另见 NFR-004。

**FR-014 失效换源与重新发现**  
打洞失败先尝试服务端中转；Peer 离线、拒绝服务、分片丢失或中转失败时，请求有界超时、退避和换源，必要时重新查询分布。中转不改变“至少 k 个有效不同索引”的条件。  
验收：下载中断开一个来源，剩余可达来源合计仍有 k 个索引时能够继续；不足时进入“等待来源”，恢复足够来源后无需重建任务即可继续。

**FR-015 暂停继续与取消**  
用户可暂停、继续、取消和重试，操作结果即时可见；取消不再安排新请求，已有缓存按用户选择处理。  
验收：连续快速操作不产生重复任务或僵死状态；暂停/取消后建议 2 秒内停止安排新传输；继续复用已校验分片。

**FR-016 跨重启恢复**  
持久化任务版本、目标位置、已校验完整分片及必要配置，重启后重新验证可复用数据。  
验收：下载中退出再启动，可继续原任务；已被删除或篡改的缓存重新下载；未完成分片重新下载时进度说明准确。

**FR-017 分片和整文件校验**  
逐片校验并隔离无效分片，重建后验证长度与完整摘要，成功前以临时文件保存。  
验收：注入错误内容后拒绝该分片并尝试其他来源；整文件摘要不符时标记失败，不能覆盖原有正确文件或显示完成。

### 6.4 UDP 传输与安全

**FR-018 可靠的分片交付**  
UDP 数据面必须处理传输块丢失、重复、乱序和超时，限制重传次数或总时限并报告失败。  
验收：在 NFR-006 的故障配置下可恢复正确文件；重复数据不重复写入或重复计算进度；来源不可恢复时最终进入可识别的等待/失败状态，不能无限忙重试。

**FR-019 速率与拥塞响应**  
发送方支持并发和速率上限，在丢包、超时或接收方压力升高时降低发送负荷，并允许健康后逐步恢复。  
验收：施加带宽限制时观察到发送负荷调整；接收缓冲有界；手动上行限速生效，不能只靠不断增加 UDP 发送速率争抢带宽。

**FR-020 会话隔离和安全传输**  
只有获准会话可读取或声明分片；传输具备身份校验、机密性、完整性与防重放能力，不自行设计密码算法。直连与中转均须满足这些约束；通过服务端转发时保留端到端文件内容保护，中转端仅处理必要路由元数据，不记录明文载荷。具体成熟协议或库在设计阶段选择；无账号不等于无会话安全，UUID 本身不承担认证。  
验收：未获准端、篡改数据、过期会话及重放请求不能被接受为有效传输；抓包不能直接读出文件明文；失败不污染任务进度。

**FR-021 请求与报文边界**  
限制报文、索引、长度、请求频率及会话资源，避免依赖 IP 分片；验证对方可达性前不得向伪造来源发送大量文件数据。  
验收：非法索引、超大长度和高频无效请求被拒绝且不会崩溃；常规实验路径中报文满足配置的载荷上限；无法完成连接验证的来源不会触发大流量响应。

### 6.5 交互与维护

**FR-022 任务状态可见**  
展示等待来源、连接中、下载中、暂停、校验/恢复中、完成、已取消、失败等状态，以及已校验进度、速率、有效来源数和失败原因；每条来源展示直连、中转建立中或中转传输状态，切换不重复计算进度。  
验收：每个第 9 节场景都有对应状态；100% 网络接收不等于完成；传输总字节数与已校验文件进度分开统计。

**FR-023 错误与恢复指引**  
区分来源不足、直连失败、中转不可达/额度耗尽、UDP 连通失败、协调 API 不可达、清单不合法、校验失败、磁盘错误等原因，并给出可执行下一步。  
验收：故障注入时展示相应错误类别及重试/选择来源/检查网络或目录的入口，不仅显示通用“下载失败”。

**FR-024 诊断与实验记录**  
输出可关联任务和会话的结构化日志与统计，覆盖分片来源、直连/中转路径和切换原因、中转流量、吞吐、重传、重建结果、调度变化及错误；默认不记录凭据和文件内容。  
验收：能从一次实验导出完成耗时、完成率、有效数据量、总传输量和调度变化；日志可支持复现实验，敏感字段按 NFR-007 检查。

**FR-025 协调服务中断处理**  
服务端失联时，区分协调 API 失联与中转数据面中断；保留任务和有效数据，恢复后重新建立合法会话、同步 UUID 绑定、状态与分布。中转不可用时不能继续声称该路径正在传输。  
验收：停止再恢复服务，不丢失已校验分片，不把旧设备状态直接当作在线；新发现请求失败有明确提示。现存直连是否继续，取决于有效会话期限和第 12 节的安全方案。

### 6.6 服务端中转

**FR-026 直连失败后的 UDP 中转**  
客户端优先尝试直连，超时或确认失败后请求同一服务端转发来源与下载方之间的 UDP 数据；来源仍须在线并实际持有请求分片。中转仅允许已验证会话及目标端点，不能成为任意地址转发器。限制每会话及全局并发、带宽、队列/缓冲和空闲期限；超额明确拒绝或排队，取消/超时后回收资源。具体额度和切换超时在设计评审确定。  
验收：阻断 Peer 直连但保留双方到服务端的 UDP 路径时，中转完成且文件一致；直连和中转均失败时有界结束尝试、保存进度并提供重试入口。伪造目标、未验证会话、超额及取消用例不造成开放中转、无限缓冲或资源泄漏。转发过程不永久保存文件或把服务端统计为分片副本。

本节与第 8 节实验目标已由项目发起人在 D-04 接受，仍须验证可行性；若需改变目标，记录原因并重新确认。平台具体版本/架构、资源配额及协议实现仍需设计细化。除专门测试网络能力外，均采用第 8 节记录完整配置的受控实验。

| 编号 | 要求与验收方法 |
| --- | --- |
| NFR-001 正确性 | 第 9 节成功场景中，恢复文件的长度及 SHA-256 与原文件一致；小文件 RS 全组合测试还需逐字节一致。任何发现的校验失败都不能计为成功 |
| NFR-002 状态新鲜度 | 心跳周期 5 秒、过期阈值 15 秒、状态扫描最长 5 秒；最后一次有效心跳后最迟 20 秒，从新任务在线候选中移除。测量以服务端接收时间为准 |
| NFR-003 控制面响应 | 在 50 个已分配 UUID 的设备、500 个文件清单、5,000 条持有关系及 10 请求/秒混合查询/上报负载下，服务端处理耗时 p95 ≤500 毫秒，连续 10 分钟无未恢复写入错误；排除公网往返，报告硬件及负载构成 |
| NFR-004 调度收益验证 | 对预先定义的异构/退化场景至少运行 5 轮，采用相同文件、分布、并发上限和故障脚本对照固定策略；完成率不下降，100 MiB 文件中位耗时目标改善 ≥10%，均匀网络中退化 ≤10%。同时报告额外字节和离散程度；达不到时保留真实结果并分析，不更换条件凑结论 |
| NFR-005 资源有界 | 单个 1 GiB 文件处理时客户端进程峰值 RSS ≤512 MiB；上行和并发可配置。记录编码、下载及恢复峰值，磁盘估算覆盖原文件、缓存、恢复临时文件和冗余开销；不能将整个文件大小线性累加到内存 |
| NFR-006 故障可恢复 | 在 3% 丢包、80 毫秒往返时延、1% 重复和 5% 乱序的明确配置下，100 MiB 文件 5 次均正确完成；再分别测试来源退出及服务重启。超出支持条件可失败，但须有界重试、保存有效进度并说明原因 |
| NFR-007 隐私和安全 | 凭据、会话密钥和文件内容不进入普通日志；公开材料不上传真实私有文件、设备 IP 或未授权个人信息。通过无效身份、篡改、重放、越权索引、路径穿越和文件覆盖用例验证边界 |
| NFR-008 可用性 | 核心操作有中文说明，任务运行中窗口保持响应；用户操作 1 秒内给出可见反馈、状态最长 1 秒刷新一次。测试大文件编码时仍能操作窗口和取消任务 |
| NFR-009 兼容性 | 首发 Windows 客户端、Linux 服务端已确认；CPU 架构与系统版本范围仍待 D-01 的设计细化；在干净目标环境安装并完成 UC-01 至 UC-04。声明 Wails 所需系统组件，不将开发机可运行等同于用户环境可运行 |
| NFR-010 可重复验证 | 后续锁定 Go、Echo、Wails、RS/传输库及构建工具版本，记录启动配置和测试数据生成方式；测试脚本、结果和需求编号可互相追溯，成功与失败结果均保留 |

## 8 验收数据与测试口径

### 8.1 已接受的实验基线

- 服务端：1 个兼具协调和中转能力的实例；参考环境为 2 核 CPU、2 GiB 内存的 Linux 主机，本地 SQLite 数据文件。最终按实际设备记录，不虚填配置。
- 文件来源：至少 3 个独立 Windows Peer；另设 1 个 Windows 下载 Peer。部分容错试验可增加 Peer，逻辑实例与实际机器数量须分别说明。
- 网络覆盖：除局域网和故障模拟外，至少完成一组跨两个独立接入网络的公网直连实验并记录 NAT 条件。课程场景涉及互联网节点；如只能使用同机或局域网演示，须先向教师确认其是否满足要求。
- RS 参数：k=4、m=2，以便枚举所有四片组合。参数不是“允许两台机器掉线”的保证，必须结合实际分片分布判断。
- 首期支持上限：单文件 1 GiB，超限拒绝并说明原因。
- 功能数据：0 字节、1 字节、非 k 整倍数大小、1 MiB、100 MiB 的确定性文件，包含中文和空格文件名、同名不同内容文件；资源测试增加 1 GiB 文件。
- 空文件建议按原长度为 0 的清单和确定性补齐数据编码，恢复后截断为 0 字节；具体库不能支持时，须在设计评审确定专门处理路径，保持用户层可发布、可下载、可验证。
- 每次实验记录操作系统、CPU/内存、依赖版本、网络拓扑、NAT 条件、限速、延迟、丢包/重复/乱序配置、种子或脚本、分片位置、参与设备与时钟口径。

### 8.2 性能比较

固定策略基线为：可达来源确定后固定分片分配与并发度，不根据后续带宽变化主动重新分配；两组均保留同样的直连/中转策略、超时、重试和失效换源能力，编码、校验和传输实现保持一致，只比较调度分配差异。单来源结果可作为辅助参考，不能替代调度策略的受控对照。

设置均匀链路、异构带宽、下载中某来源降速、单来源离线四类场景。下载耗时从用户确认任务开始，到最终文件验证并写入成功结束；同时记录连接、传输、校验和恢复的分阶段耗时。整组试验按预定脚本执行，报告中位数、范围、失败次数、重传和冗余流量。

多源下载并不保证比单来源快：总下行带宽、编码/校验成本、源端上行、冗余获取和 NAT 条件都可能限制收益。测试结论应描述适用条件。

中转增加服务端带宽成本与共享瓶颈。除直连实验外，单独记录中转及混合路径的服务端 CPU/内存、并发、入站/出站字节、耗时与失败率；对照实验保持相同中转额度与路径条件，不混合统计出虚假的调度收益。第 7 节原有目标保持不变，但尚未确认单独的中转吞吐量门槛，不能编造该门槛或达标结果。新增覆盖“直连失败但中转成功”“两条路径均失败”“中转限额/服务重启”和“来源离线或独立分片不足”等用例。

| AT-17 | 中转请求中的伪造端点、无效会话和超额请求被拒绝/限流，取消及空闲超时回收资源；中转抓包/普通日志无文件明文，未增加永久文件副本 | FR-019、FR-020、FR-021、FR-024、FR-026；NFR-007 |
| AT-18 | 中转服务健康但来源离线或有效不同索引少于 k 时，仍等待来源；中转不能制造缺失分片，足够来源恢复后可继续 | FR-007、FR-014、FR-022、FR-026 |

## 10 技术可行性与设计建议

本节解释需求的约束，不提前确定数据库表、消息字段、目录结构或算法实现。

- **Echo v5 与 Wails 3**：官方文档当前均要求 Go 1.25 或更新版本；Wails 3 当前处于 beta 阶段。建议验证目标平台后锁定具体依赖版本，保留升级风险。[T-01][T-02]
- **客户端职责划分**：建议 Wails 界面负责交互和状态展示，由 Go 服务承担编码、磁盘、调度和 UDP 工作，通过绑定/事件交互，避免长任务阻塞界面。界面前端技术栈尚未选定。[T-02]
- **STUN 与打洞**：STUN 是 NAT 穿透工具，不能独立提供完整穿透方案；还需会合协调、候选交换、双向探测、超时和保活。对称映射、端点相关过滤或 UDP 禁止等环境可能失败。简单 STUN 打洞不应标注为完整 ICE；若采用 ICE，应另行覆盖它的完整协议范围。[T-03][T-04]
- **UDP**：本身不保证交付、顺序、去重、拥塞控制或安全。FR-018 至 FR-021 约束的是结果；后续应先评估成熟的 UDP 传输与安全组件，再决定是否自定义上层格式。应用载荷上限需结合路径 MTU 与协议开销，不能假设“大分片可以直接装入一个 UDP 包”。[T-05]
- **RS**：k 个不同有效分片的恢复性质依赖一致编码参数与格式。RS 解决擦除恢复，不等于鉴权、加密、自动定位任意恶意损坏，也不取代 UDP 重传；应先校验并排除坏片，再恢复并校验完整文件。[T-06]
- **SQLite**：WAL 模式支持读写并行，但同一时刻仍只有一个写入者。短事务、心跳写入合并、忙重试和合理索引是待验证的设计选项；本期不承诺多协调实例写共享数据库。[T-07]
- **MVP 服务端中转**：已确定由 Linux 服务端承担直连失败后的中转数据面。具体成熟协议/库待设计选择，不等于已经选定 TURN；保留 UDP 约束、端到端保护和 FR-026 的资源边界。中转带来服务端带宽成本与单点瓶颈，无法恢复离线来源、缺失分片或被全面阻断的 UDP 路径。
